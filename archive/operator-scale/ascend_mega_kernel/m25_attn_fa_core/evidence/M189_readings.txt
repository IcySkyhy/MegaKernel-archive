M189 —— B3（m15_attn_fa_core.h）**cube 数据通路数值根因的定位与修复**
================================================================================
日期：2026-10-05。设备：Ascend950PR / NPU0（每档各自 `flock -w 300 /tmp/npu0.lock`，
进锁先 `npu-smi`，`timeout` 在锁内）。构建：`m25_attn_fa_core/build/m25_attn_fa_core`
（`cmake --build` rc=0 / 0 error，唯一告警来自被 include 的 `m15_hc_layer.h:740/766`）。

--------------------------------------------------------------------------------
0. 结论（一句话）
--------------------------------------------------------------------------------
B3 四档全 FAIL 的根因是 **`L1 -> L0B` 的 BufferID 交接被放错了作用域**：BMM1 的 `ks`
（2×128 k 半块）与 BMM2 的 `nh`（2×128 维半块）循环里，**生产侧（`PIPE_MTE1`）的
`Acq/Rls` 被提到了循环之外**，于是 M 侧两条 `Mmad` 都等到循环结束才拿到 L0B、
**都读到循环最后一次装载的结果**：
  · BMM1：两个 k 半块都用了**第二个半块的 K** ⇒ `S = Q·Kᵀ` 系统性错（M185 看到的 maxdiff≈43）；
  · BMM2：两个 nh 半块都用了**第二个半块的 V** ⇒ PV 系统性错（`out[0] ≠ V[0]`）。
修法 = 把 `Acq<PIPE_MTE1>(B_L0/B_K)` / `Acq<PIPE_MTE1>(B_L0/B_V)` 与其配对的 `Rls`
**挪进循环、每个半块装载后立即 release**（与 donor `m10_attn_decode` BMM1 的 per-half
交接同款）。

--------------------------------------------------------------------------------
1. 定位过程（**只看最终结果 + 已有的 scratch/输出面，不新增探针 kernel**）
--------------------------------------------------------------------------------
人类口径：「最好不要用探针，就看最终的结果去分析和定位」「把中间量 dump 到已有的
scratch/输出面再在 host 侧比对，不要新增探针 kernel、不要引入额外同步」。本 mission 照此：
用 **已有的 `pScratch`（`pGM_`，本段已声明但不再使用）** + **已有的 cube `Fixpipe` L0C→GM**
（复刻 donor `m10_attn_decode` 的 `FixpToGmDbg` 形态，`srcStride=mSize / dstStride=nSize`
与已验证的 `m10_mmadprobe` 同口径）落盘 AIC 的 BMM1 L0C（= 原始 `Q·Kᵀ`，无新增跨核同步、
无新增 kernel）。**诊断代码全部在提交前移除**（见 §5）。

### 1.1 复现（与 M185 逐位一致）
`check_ref.py`：`m=64` `core` **FAIL** `over=371949/393216 maxratio=195.5818`；
`OUT_FNV64=0x9294cefcc027e633`（与 M185 同名同值）⇒ 挂死已解、数值仍错，确认现状。

### 1.2 逐项排除（每一步一个小实验，只动一个变量）
| # | 假设 | 实验 | 读数 | 判定 |
|---|---|---|---|---|
| 1 | K/V 的 L1 `TPosition` 声明（`A1` vs donor 的 `B1`）错 | 把 `l1K/l1V` 声明改 `B1` 重建重跑 | `OUT_FNV64` **逐位不变** | **排除**（本平台 A1/B1 同址） |
| 2 | 多矩阵 `Nd2Nz`（`ndNum=nb`）与单矩阵形态不等价 | 打开既有 `M25FA_GEO_ONEMAT`（并修正其源偏移 `b*16*page` → `b*page`，见 §4.2） | 修正后与多矩阵**逐位一致** | **排除**（两种形态等价） |
| 3 | A 操作数（Q）几何错 | `K ≡ 1`（全 1）⇒ `S[m,n] = Σ_k A(m,k)` 与 host 行和逐元素比 | `maxdiff = 0.0` | **排除**（A 行和精确） |
| 4 | B 操作数（K）的 k 轴映射错 | `Q = 单位阵`（A=δ）；`K[n,d] = 1+d/128`（bf16 位型 `0x3F80|d`，精确）⇒ `S[m,n] = 1 + D(m)/128` | 默认参数下 `S ≡ 0`（`D(m)` 解出 = -128，即读到 dims≥128）；**仅把 k 半块源偏移乘子置 0** 时 `D(m)=m` 正确 | **定位：B 的 k 半块读到了错的 L0B** |

### 1.3 机制
上面第 4 步的读数是决定性的：`S` 只与 **k 半块源的偏移乘子** 有关。把它置 0（两个半块都
从 `l1K + 0` 读）时 `S` 才对 —— 说明 **`ks=0` 的那次 `Mmad` 实际读的是 `ks=1` 装载的 L0B**，
即生产侧（MTE1）的释放被推到循环之后，M 侧的 acquire 因此等到循环全部结束才放行。
BMM2（`nh` 循环）是同一形态 ⇒ 同样错。对照 donor `m10_attn_decode` 的 BMM1：
它在循环内**每个 ks 装载后立刻 `Rls<PIPE_MTE1>`**、随后 M 侧 `Acq<PIPE_M>`。

4. 顺带发现 / 仍存疑

### 4.1 `FacGmToL1Nz` 多矩阵与单矩阵等价（第 1.2 表第 2 行）
修正 `M25FA_GEO_ONEMAT` 的源偏移后，两形态输出**逐位一致**（`0x14d9248b5f4dec5b`，m=64）。
⇒ 既有的「多矩阵形态是自拼的、可疑」这条**不再是失败候选**（M185 exclusions 第 12 行）。
### 4.2 `M25FA_GEO_ONEMAT` 的源偏移真 bug（已修）
原代码把每页源偏移写成 `kOffElem + b * FAC_BLK_TOK * (KV_BLOCK_BYTES/ELEM)` = `b*16*page`，
比正确值大 16 倍（读出 KV 平面之外）⇒ 该宏档原本必错。**已改成 `b*page`**；修后与多矩阵一致。
（这是默认关闭的对照宏，修复不影响默认路径。）
### 4.3 host `EnsureDir` 非递归（harness，与本 mission 无关）
`m15_attn_fa_core_host.h::EnsureDir` 只 `mkdir` 一层；传「`<out>/r1_m16`」这类
**父目录不存在**的 `argv[2]` 会在 `mkdir <dir>/m64_core` 处 rc=42。本档验证时**先建父目录**。
（不影响 M185 记录的 `M25FA_OUT` 未被读取那条 —— 那条仍成立。）

6. 同 scope 尾巴（塔指派的收尾项）
--------------------------------------------------------------------------------
### 6.1 `M25FA_OUT` 不生效 —— **真 bug，已修**（`m15_layer_loop/m15_attn_fa_core_host.h`）
* **修前**：`Main()` 只认 `argv[2]`，从不读 `M25FA_OUT`；而 `README.md` 与 `run_checks.sh`
  都按 `M25FA_OUT` 工作 ⇒ 用户按文档设置**不生效**。
  实测（`M25FA_M=64 M25FA_OUT=/tmp/m189_before <bin> core`，无 `argv[2]`）：
  `ls /tmp/m189_before` ⇒ `No such file or directory`；输出落在默认 **`m25_attn_fa_core/out/m64_core`**。
* **修法**：落盘根优先级改成 **`argv[2]` > `M25FA_OUT` > 默认 `m25_attn_fa_core/out`**；
  另把 `EnsureDir` 改成**逐级创建父目录**（`run_checks.sh` 的 `$OUT/rep<i>/` 与多层
  `argv[2]` 需要它；修前非递归 `mkdir` 在这些路径上 rc=42）。
* **修后实测**（同一条命令）：`ls /tmp/m189_after/m64_core` ⇒ `out.bin / params.txt / q.bin /
  k.bin / v.bin / mode.txt` 齐全；默认 `m25_attn_fa_core/out` **不存在**。
* **端到端见证**：`M25FA_M="16,64" M25FA_REPEAT=2 bash m25_attn_fa_core/run_checks.sh`
  ⇒ `[core rep1/2 m=16/64] VERDICT=PASS`、三个负向对照全 `FAIL`、
  `m=16/64 的不同 sha256 数 = 1`、**`RUN_CHECKS_RC=0`**（修前这个脚本按 `M25FA_OUT` 组织路径、
  二进制却不认，会全部落到默认目录 ⇒ 找不到 `out.bin`）。**未改任何判据/台架语义。**
