## 0. 结论速览（先读这 8 条）

1. **15.51 ms/层 里几乎没有"固定开销"**：对归档 4 档做两点线性拟合（H=48、chunk 数 3 与 65），
   得**每 chunk 边际 ≈ 238.1~238.5 µs**、**截距（launch + 状态首尾） = 13.6~19.2 µs = 总时间的 0.09%~0.13%**
   （两组端点的口径与各自读数见 §2.2）。⇒ 15.51 ms ≈ 65 × 238 µs 的**纯 chunk 本体计算**，
   **不是**"每步固定开销"问题。对 M33 §9 存疑 5 的答复因此是：
   **向量域路线的"每步固定开销"已被标定为 ≤0.22 µs/步（不可当 0，也不构成瓶颈）**。
2. **15.51 ms 可以按定义拆成三个因子**（用 m18 README 的归档指令模型，`README.md` 的 §4.7）：
   **3.27 ms（必要 MAC 以 64 lane/FMA、1 指令/cycle 发完）
   × 2.21（算法指令膨胀：实发 2.0×10⁵ vs 必要 9.1×10⁴ 条/chunk-head）
   ÷ 0.466（实测发射率 0.466 指令/cycle，@假设 1.8 GHz）= 15.51 ms**（复算式与输出见 §2.4）。
   **必须带一句定性（第 1 轮复审 P2-1 指出）**：这是**按定义做的分解，不是校验** ——
   发射率 `0.466` 本身就是从实测时间反推的，所以 `3.27 × 2.21 ÷ 0.466 ≡ 15.514` **是代数恒等式，不带信息量**。
   本报告**真正独立的见证是 §2.2 的两点拟合 + 第三点（H=8/nc=1）的样本外预测自检**（残差 0.36%~1.37%）。
3. **访存不是瓶颈**：每层 GM 流量 ≈ **416.8 MB** → 0.26 ms（名义 1.6 TB/s）～0.38 ms（实测 1.1 TB/s），
   占 15.51 ms 的 **1.7%~2.5%**。**AIC 在整段 100% 空转**、AIV 占用 48/56 = 85.7% —— 这两条都是
   **容量**问题，不是当次时间的直接系数；但 **AIC 空转正是 (a)(b) 两条路线的量级差额本身**。
4. **与 `docs/15` 的 1.37 ms/层 对齐必须先对齐口径**：m18 **只覆盖 chunk core**（P4–P9），
   不含 in_proj（P0）/ out_proj（P11）。逐口径给倍数是：
   - 对 **整个 GDN 层**（505.9 GFLOP，含 in/out proj）的下限 1.37 ms：**11.3×**（M103 引用的是这一条）；
   - 对 **chunk core 自己**的 cube roofline（`docs/15` 的 15.6 GMAC → 31.2 GFLOP → 0.0848 ms @368 T）：
     **183×**（按 m18 自己的必要 MAC 36.0 GFLOP 算：**159×**）；把 368 T 按 28/36 折算（×1.28）后
     **143× / 124×**。
   ⇒ "差一个数量级"这个说法，**只在"整个 GDN 层"口径下成立；同段同口径下是两位数量级（1.2~1.8 × 10²）**。
5. **VF 路线追不上 cube —— 这一点与假设口径无关，但倍数区间很宽**（r1 复审 P2-4 订正了标签，
   r2 复审 P2-2 又指出本条的区间写法与 `§3.3` 不一致 ⇒ 现与 `§3.3` 逐字对齐）：
   - **口径甲（1~2 指令/cycle 假设）**：必要 MAC 的下限 **1.63~3.25 ms** ÷ cube 同段下限 **0.0848~0.1252 ms**
     ⇒ **13~38×**。**跨度的取法**：{1.627, 3.254} ms 与 {0.0848, 0.1252} ms 两两相除得
     {19.2, 13.0, 38.4, 26.0}，**最小 13.0、最大 38.4** ⇒ **13~38×**（`§3.3` 表里的
     "26~38×（@1 指令/cycle）" 与 "13~19×（@2 指令/cycle）" 是它的两个子区间）；
   - **口径乙（VEC FP32 峰值，`roofline_model.md` 的 56 核 × 512 FLOPS/cycle）**：48 个 AIV 的峰值
     24.6 TFLOPS（@1 GHz）~44.2 TFLOPS（@1.8 GHz）⇒ VF 下界 **0.814~1.465 ms** ⇒ 比值 **6.5~17×**。
   ⇒ **给 B1 定规模时应该用保守端（≥~6.5×，即"至少 ~7×"），不要按 38× 定**。
   **方向不变**：**(a) 不是"待优化的性能基线"；(b) 是唯一能切断 65 步串行链的路线**（见 §3.3 与 §4）。
6. **"是否必须二选一"的答案：不是必须，而且"把扫描步做成可替换接口"在硬件与现有代码结构下可行 ——
   但有三个前提**（缝必须划在**收缩原语**层而不是"整段扫描"层；**状态 S 的归属必须进接口**；
   flagId/BufferID/峰值断言必须在 Wave A 一次划段），**外加一条人类裁决给出的新前提**：
   **缝的交付实现只能是 mmad，VF 实现只能当对照**（见 §4.3/§4.4/§10）。
   做不到第一条时，"可替换"会退化成"整段重写"。
7. **B1 的头号设计风险是 mmad 的精度，不是性能**（§11）：chunk 扫描里数值最敏感的三处
   （**chunk 内 cumsum / `(I+L)^{-1}` 三角求解 / 状态 S 的缩放与递推**）若操作数只能是 bf16，
   精度够不够取决于「**cube 能不能吃 fp32 操作数**」—— 塔已派 **M106** 探针裁决。
   **本文件不猜 M106 的结论**，只给出两种分支下 B1 各要怎么做（含 hi/lo 双 bf16 拆分这条备选）。
8. **本 mission 没有上设备**（归档读数已足够回答 §2，且设备队列上是 M101 的进程）——**未做今日复跑**，
   因此不能声称"15.51 ms 今日仍可复现"。这是本报告的一个明确边界（§8）。

### 1.2 m18 是什么（一句话定性，给不熟悉它的读者）

`m18_gdn_prefill` 把 GDN decode 的逐 token 递推换成 **BT=64 的分块扫描**：48 个 value head 各占一个 AIV
（`m18_gdn_prefill.asc` 的 `for (uint32_t hv = bid; hv < numHeads_; hv += nAiv)`，`nAiv = 2 × AIC 数 = 56`），
每个 AIV 串行走完自己 head 的 65 个 chunk。**算法已证**（4 档 PASS，判据是自建 numpy float64 逐句参考），
但它是：
- **fp32 全程**（为对齐 fp64 紧容差判据）；
- **AIV-only**：核体在 `if ASCEND_IS_AIV { … }` 里，AIC 那条分支只有一个注释与 `PipeBarrier<PIPE_ALL>()`，
  **无任何计算、无任何访存、无 cross-core flag**（4 个 BufferID：`BUF_BLK=0`/`BUF_ST=1`/`BUF_SO=2`/`BUF_PR=3`）；
- **独立 CMake 工程**（`m18_gdn_prefill/CMakeLists.txt` 首行自述"不依赖仓库顶层 CMakeLists.txt"），
  只 include 框架头（`acl/acl.h` / `kernel_operator.h` / `c_api/asc_simd.h` / `reg_compute/kernel_reg_compute_intf.h`），
  **不 include 任何 m15 头**。

### 2.2 【任务 1 的主交付】每 chunk 从"固定开销"里分离出来

H=48 有**两个不同的 chunk 数**（3 与 65），且两次都在同一进程同一二进制里跑完
⇒ 可以做**两点线性拟合** `t(nc) = a + b·nc`，把"每 chunk 边际成本"与"截距"分开。

**先把输入口径声明清楚**（第 1 轮复审 P2-2：本节原表与 §8.3 贴的 C2 命令用了不同的 `t65`，
两条都能复现但没声明用的是哪一组 ⇒ 读者按 C2 去核本节会核不上）：

| 端点 | 档位 | probe 状态 |
|---|---|---|
| `t3`（nc=3） | `all48`（H=48, T=129） | **只有 probe 开**这一种（归档里没有 `all48` 的 probe 关对照） |
| `t65`（nc=65） | `target`（H=48, T=4097） | 归档里**既有 probe 开、也有 probe 关**（§2.1 的最后一行） |

（截距 ≤19.3 µs、占比 ≤0.13%，边际 ≈238.1~238.5 µs），**§3.2 ⑨ 引的是变体 B 的那三个截距**
（原文写 14.565/17.274/19.226 = B 组）—— 本文件保留它们，但**在此声明它们来自变体 B（混用端点）**。

**模型自检**（第三个数据点，不同 head 数）：用变体 A run1 的 `a`、`b` 外推 `one` 档（H=8，nc=1）
得 **0.2521 ms**，归档实测 **0.254 ms**，残差 **0.76%**（变体 B 为 0.51%）。⇒ 三个结论同时成立：
- **每 chunk 成本对 head 数不敏感（8 头与 48 头同量级）** —— 因为 1 head/AIV、head 之间完全并行，
  238 µs 是**单个 head 的每 chunk 延迟**，与并行宽度无关；这是**样本外**预测，不是拟合内的自洽；
- 线性模型在 1~65 chunk 的范围内可用（残差 ≤1.4%）；
- **这两条是本报告里唯一带"独立见证"性质的量化证据**（`t8` 没参与拟合），
  与 §2.4 的"按定义分解"不同（后者是恒等式，见 §2.4 的定性）。

**⇒ 回答任务 1 的"多少是真正 workload、多少是固定开销"**：
**15.51 ms 里 ≥99.85% 是 chunk 本体的计算**（65 × 238.1 µs ≈ 15.48 ms 中的边际部分），
**固定/启动/状态首尾 = 13.6~19.2 µs（0.09%~0.13%）**；**设备空转不计入这 15.51 ms**（它是容量，见 §2.6）。
"访存瓶颈"这一条见 §2.5（也不是）。

> **对 M33 §9 存疑 5 的答复边界**：m18 标定的是**向量域**每步（0.22 µs/步的固定开销上界）。
> M33 存疑 5 真正担心的是 **mmad/高阶 API 路径的 44~69 µs/call `IterateAll` floor**（`docs/15` §3.1 引的
> `cannbot-knowledge/.../ol_246_...md:29`），而 **m18 里没有 mmad、没有 `IterateAll`** ⇒
> **那条 floor 在本机 `LoadData`+`Mmad` 路径上仍然未标定**，见 §7。

### 2.3 每 chunk 的指令 / MAC 预算（逐原语，从核体读出）

m18 README §4.7 给的归档模型是"**每 chunk-head ≈ 2.0×10⁵ 条向量指令**、**必要 MAC 5.8M**"。
本 mission 从核体的 VF 原语**逐条重算**做交叉见证（每个 helper 的每行指令数由循环体直接数出；
`VL = 64` fp32 lane/寄存器，`RBLK = 4`）：

| 每 chunk-head | 指令 | 说明（一次 4 行块的 `LoadAlign` + 4×BRC + 4×`MulAddDst` = 每 256 个 MAC 花 9 条指令） |
|---|---|---|
| `GemmBT` kk `[64,64]` inner=128 | 20,624 | 16 块 × (1 `Muls` + 4 载 + 128×(Gather+Adds+4 BRC+4 FMA) + 4 存) |
| `TrilSolveVF` u（64 行 × 329 条/行） | 21,056 | 行前代；每行 2 `Duplicate` + 64×(1 BRC+2 载+2 FMA) + 6 + 1 `LocalMemBar` |
| `TrilSolveVF` w | 21,056 | 同上（两个右端各一次） |
| `GemmAA` d = u − w·S ×2 半 | 37,120 | rows=64, inner=128 |
| `GemmAA` o_part = q′·S ×2 半 | 37,120 | rows=64, inner=128 |
| `GemmAA` o += AB·d ×2 半 | 18,688 | rows=64, inner=64 |
| `GemmBT` AB = q·kᵀ | 20,624 | rows=64, inner=128 |
| `GemmTA` S += kᵀ·d′ ×2 半 | 37,376 | rows=128, inner=64 |
| `CumSumExpVF` + `GammaStrictVF` + `GammaInclVF` | 555 | Hillis–Steele 6 轮 + 两次 Γ（`exp` 传递） |
| 逐行/逐元素缩放 + 归零 + 显式 `MemBarVL` | 4,510 | `RowScale1/2`、`CopyScale2`、`Mul2D`、`StateScale`、`ZeroVF`、`ConstScale2` |
| **合计（本 mission 重算）** | **218,729** | 与归档模型 200,000 **同量级（+9.4%）** |
| **必要 MAC（本 mission 重算）** | **5,767,168** | 与归档模型 5.8e6 一致（−0.6%） |

两个结构性事实（**这是选型的直接依据**）：
- **收缩类占 97.7%**：`GemmAA/BT/TA` 171,552 + 行前代 42,112 = 213,664 / 218,729；
  其余（cumsum / Γ / 逐行缩放 / 归零）= **2.3%**。⇒ **m18 的 15.51 ms 几乎全是"可以搬到 cube 上的那类运算"**。
- **每 chunk 的 mem_bar = 154 次**：**128 次来自两次行前代**（`TrilSolveVF` 每行末尾一条
  `LocalMemBar<MemType::VEC_STORE, MemType::VEC_LOAD>()`，2 × 64 行），**26 次是 chunk 体里的显式
  `MemBarVL()`**。m18 README §4.7 说的"每 chunk 128 次 mem_bar"**正好等于 2×BT**，可复算（见 §8 的 C4）。

### 2.4 三因子分解（**按定义分解，不是校验** —— 第 1 轮复审 P2-1）

用**归档模型**（2.0×10⁵ 条/chunk-head、5.8M MAC/chunk-head）与实测 15.514 ms：

```
注 1：下面用 238.7 µs = 15.514 ms / 65 作为"每 chunk 平均"；§2.2 变体 A run1 拟合出的边际是 238.468 µs。
      两者差 0.1%（平均含截距的 65 分之一，边际不含），不是两个数、是同一件事的两种取法。
注 2（**重要，本节标题因此改名**）：下面的"发射率"是从实测时间反推出来的
      —— issue := INSTR / (t65/65) / GHz，而 ideal × algo = (MAC/LANES)/GHz × INSTR/(MAC/LANES)
      = INSTR/GHz。故 ideal × algo / issue ≡ (INSTR/GHz) / (INSTR/(t65/65)/GHz) = t65/65，×65 恒等于实测 t。
      ⇒ **这是代数恒等式，不可能不成立，零信息量。它只能读作"把实测时间按定义拆成三个因子"，
      不能读作"模型被实测验证"。** 本报告真正独立的见证是 §2.2 的两点拟合 + 第三点（H=8/nc=1）
      的样本外预测（残差 0.36%~1.37%）。

必要指令/chunk-head = 5.8e6 / 64 lane = 90,625 条
理想时间（1 指令/cycle @1.8 GHz 假设时钟）= 90,625 / 1.8e9 = 50.35 µs/chunk
                                              → ×65 = 3.273 ms/层
算法指令膨胀 = 2.0e5 / 90,625 = 2.207×
实测发射率 = 2.0e5 / 238.7 µs = 0.838 G 指令/s/AIV → ÷1.8 GHz = 0.466 指令/cycle
恒等式：3.273 × 2.207 ÷ 0.466 = 15.514 ms  ← 与归档实测 15.514 相等（**恒等，非校验**）
```

**这个分解仍然有用的地方**（把它当"分解"而不是"验证"时，它回答的是"修哪一项能拿回多少"）：

| 只修这一项 | 结果 | 可回收 |
|---|---|---|
| 发射率 → 1.0 指令/cycle | 15.514 → **7.22 ms** | 8.29 ms |
| 算法膨胀 → 1.0× | 15.514 → **7.02 ms** | 8.47 ms |
| 两项都修 | → **3.27 ms** | 12.24 ms |

注意：这两条反事实**同样带假设**（"指令数不变、只是发得更快" / "发射率不变、只是指令更少"），
且**不能相加**（同一个"理想项"的两种切法）。

**发射率损失的归因（m18 README §4.7）**：UB 装载延迟 + BRC/Gather 依赖链 + 每 chunk 154 次 mem_bar。
**本 mission 无法把这三者分开**（归档读数没有对应档位）⇒ 见 §7 的"需要什么实验"。
**注意 0.466 是"果"不是"因"**：它与 154 次 mem_bar、与 Gather/BRC 的串行依赖是同一条因果链上的两端。

### 2.5 访存：不是瓶颈（量化）

每 chunk-head 的 GM 流量：MTE2 = k(32,768 B) + q(32,768 B) + v(32,768 B) + g/β(512 B) = **98,816 B**；
MTE3 = o(32,768 B)；（状态 S 每 head 只首装/尾写一次 = 2 × 65,536 B，已计入 §2.2 的截距）。

```
每层 = 48 × (65 × (98,816 + 32,768) + 2 × 65,536) = 416.8 MB
      → 0.261 ms @1.6 TB/s（名义）  /  0.379 ms @1.1 TB/s（docs/03 的实测值）
      = 15.514 ms 的 1.68%  /  2.45%
```
⇒ **m18 是纯算力/发射受限，不是访存受限**（与"向量域跑小矩阵乘"的定性一致）。

**"无跨 chunk 流水"的可回收量给个上界**：README §8.7 说单 head 状态 64 KB 常驻 UB 导致**没有第二份 slab
做跨 chunk 双缓冲**，即下一 chunk 的 MTE2 不能与本届计算重叠。可按每 AIV 的带宽份额估上界：
`(98,816 + 32,768) B ÷ (1.6 TB/s ÷ 56 AIV = 28.6 GB/s) = 4.61 µs/chunk → 0.299 ms/层（1.93%）`。
⇒ **即便把跨 chunk 流水做满，上限也只有 0.30 ms**；它与 §2.4 的"发射率"项**重叠**（装载延迟正是发射率损失的嫌疑之一），
**不可与之相加**。

### 2.6 AIC 空转与 8 个空闲 AIV 的正确口径

- **AIC**：整段 GDN 相位 **28 个 AIC 零工作量**（核体只有 `if ASCEND_IS_AIV` 分支，AIC 侧仅一个
  `PipeBarrier<PIPE_ALL>()`）。这是**容量**：它不直接产生 15.51 ms 里的一项，但它是 (a)(b) 两条路线
  **量级差额本身**（§3）。机会成本可写成 `28 AIC × 15.514 ms = 433.8 AIC·ms/层`。
- **AIV**：48 个 value head 用掉 48 个 AIV，**8 个 AIV 立即早退**（占用 48/56 = 85.7%）。
  由于"每 chunk 延迟与 head 数无关"（§2.2），**这 8 个空闲线程并不能换来更短的时间**；
  它们是**可用于别的相位/别的段**的空闲宽度（但受 §4.1 的 UB 相位窗与同步 id 约束）。

### 3.1 先对齐口径：m18 只覆盖 chunk core

> "**在向量域实现**时每步只有 1-2 µs"这个量级。两条串行链的长度也不同（m18 = 65 步，

**结论怎么读（这是给 B1 定规模用的）**：
- **方向不变**：在任何 ≥6.5× 的口径下，**"用向量域做这些收缩"都追不上 cube**，
  所以 (a) 不可能是性能路线、(b) 仍然是唯一能切断 65 步串行链的路线。
  **这条方向性结论不需要先知道 AIV 峰值口径**（`roofline_model.md:24` 的每核 512 FLOPS/cycle、
  官方 AscendC 规格的 256 B/cycle、ops-math 的 47 T FP16 —— 三个口径给出的每核值都在
  0.42~0.51 TFLOP/s 之间，见 §8.5 #2）。
- **定规模要用保守端**：区间是 **≥~6.5×（峰值口径）~ 38×（1 指令/cycle 假设口径）**。
  **不要按 38× 给 B1 定规模**；按 "**至少 ~7×**，量级更可能在 7~40× 之间" 来定，并把
  "需要一次 AIV 峰值标定来收窄"写成显式前置（§7-2）。

**"人类裁决：矩阵乘法一律 mmad"下的读法**：本节的倍数只用来回答"VF 能不能当性能路线"——
**答案是"不能"**，这正是人类裁决与本节一致的依据；而在裁决生效后，本节的倍数**不再是选型依据**
（选型已定），只作为"为什么不需要为 VF 的性能做优化投入"的量化背景（见 §10）。

**一条附带发现（措辞已按复审收紧）**：`docs/15` §3.1 自己写的是
"cube 对 bf16 友好、**fp32 的 cube 峰值只有 24 TFLOPS ≈ bf16 的 1/15**，见 roofline:28"
（`docs/15-prefill-design.md:319`）—— 即 **`docs/15` 认为 cube 有 fp32 模式（慢 15×）**；
**异类是 m18 README §7 的"3510 的 cube 只能吃 bf16 操作数 + fp32 累加"**。
⇒ 更准确的说法是"**两处表述不一致、需一次最小实验裁决**"，而不是"不可能同时为真"。
**这条直接决定 (b) 的验收基准形态**：
- 若 cube **能**吃 fp32 操作数：chunk core 在 cube-fp32 上 ≈ `31.2 GFLOP ÷ 24 T = 1.30 ms/层`
  （= `0.0848 × 368/24`）——**比峰值口径的 VF 下界（0.81~1.47 ms）同量级甚至更快**，
  而且**保住了 fp32 的紧容差判据**；
- 若 cube **只能**吃 bf16：则 (b) 要么把判据形态从"fp64 紧容差逐句参考"换成"bf16 三方 cross_check"
  （m18 README §7 的自述），要么走 **hi/lo 双 bf16 拆分**仿真 fp32（见 §11）。
⇒ 已按纪律单列 finding 给塔（见 §8.5 #1）；**塔已派 M106 探针裁决**，本文件不猜结论（§11）。

## 4. 选型建议（`mix(1,2)` 融合形态下）

### 4.1 决定"能不能做成可替换接口"的六条硬约束（全部有锚点）

| # | 约束 | 事实与锚点 | 对 (a)/(b) 可替换性的影响 |

### 4.3 是否必须二选一（**已按人类裁决改写**：交付实现只能是 mmad）

**不是必须二选一**，但"可替换"有三个粒度，选错粒度就退化成"整段重写"：

| 粒度 | 缝的形状 | 可行性 | 判断 |
|---|---|---|---|
| **G1：整段替换**（一个 `GdnPrefillSegment::Run(...)` 两种实现） | 最粗 | 可行但**没用**：缝在整段上就等于把 chunk 循环、UB 布局、同步一起换，等于重写 | ✗ |
| **G2：收缩原语层**（**6 个收缩**各一个缝函数 + `Scan_SolveG` 被调用 2 次 + 2 组非收缩原语；见 §4.4 的逐调用点清单） | 中 | **可行，而且正是 `docs/15` §3.1 混合表在做的事** —— 那张表按运算类型分了 mmad / VF 两列。把那张表从"设计描述"提升成"代码里的接口"，就是这条缝 | **✓ 推荐（塔也认可这条）** |
| **G3：逐算子实现**（连 cumsum/Γ 都做两个版本） | 最细 | 可行但**没收益**：非收缩部分只占指令数 2.3%（§2.3），做两套只增加编译时间与指令 cache 压力 | ✗ |

**G2 的价值必须重新定位（人类裁决之后，塔明确要求把这段写进文档）**：

- **缝函数结构本身仍然成立且重要**：它让 6 个收缩各自独立、可分别替换、可分别验证；
- **资源登记也必须进接口**：flagId 段 / BufferID 段 / UB·L1·L0C 峰值断言位 / `GdnStateHome`（§4.4）；
- **但 VF 那一支不能作为交付形态**：按人类裁决「凡是涉及矩阵乘法的操作都需要用 mmad 实现」，
  **不存在"先落 VF 保正确、之后再换 mmad"的阶段**。VF 实现只允许作为
  **对照 / 参考实现**（用来给 mmad 版做交叉见证、或在 mmad 未就绪时定位问题），
  **不得出现在交付路径上**，也不得被排成某个 milestone 的产物。
- ⇒ §4.3 原文"当某个收缩的 mmad 版还没写出来时，缝上挂 VF 版"**作废**。
  正确的形态是：**缝上挂 mmad 版；未实现的收缩就是"未实现"，不允许用 VF 顶上交付**
  （可以留 VF 对照，但必须与"已交付"这个状态显式区分开）。

### 4.5 选型建议（**已按人类裁决改写**）

**结论：选型已由人类裁决给出，本节的职能从"建议选哪条"变成"裁决生效后 B1 该怎么落"。**

裁决（逐字）：**「凡是涉及矩阵乘法的操作都需要用 mmad 实现，不管 M=1 或者是多大」**。

1. **B1 从第一天就是 mmad 实现**。不存在"B1-a 落 VF、B1-b 再换 mmad"的两段式。
   ⇒ 本文件 §5.1 原文的 ②/③ 两段**作废**，已改写（见 §5.1 与 §10）。
2. **代价必须承认**（不是"mmad 没有代价"）：mmad 路线要付三笔 ——
   ① **判据形态可能改变**（取决于 cube 能否吃 fp32 操作数，§3.3 / §11）；
   ② **cross-core 同步**（有"pipe 类必须匹配核型"那类挂死面，§4.2）；
   ③ **公式脆弱面**（`docs/15` §3.1 被 M49 订正过三处符号/掩码/`e^ĝ` 口径，下游照原文实现在历史上踩过坑）。
   这三笔都要在 B1 的设计里显式处理，而不是指望"先 VF 保正确"。
3. **m18 的正确定位随之收窄**：它**仍是**（a）**判据/参考的 donor**（numpy fp64 逐句参考可直接复用）、
   （b）**VF 对照实现的 donor**（`CumSumExpVF` / `GammaStrictVF` / `TrilSolveVF` 可原样复制）；
   但它**不能**是"待优化的生产段" —— 这一点与人类裁决一致（VF 不是交付形态）。
   **注意 `Scan_SolveG` 与两类非收缩原语在裁决下仍然允许是 VF**（它们不是矩阵乘法），
   见 §10.4 的逐条裁决映射。
4. **本文档 §4.4 的缝函数表 = B1 的接口契约草案**。B1 的 Wave A 契约条目就是它 + 三件资源 + `GdnStateHome`。
   **它必须与 `docs/15` §3.1 的混合表逐条对齐**（这是 P-GDN-5 的债，见 §5.2）。

**这个建议在什么条件下失效（提前说清）**：
- 若 §7-4 的"UB→L1 操作数通路"在真机上不成立（交付实现无法消费 AIV 在 UB 里产出的 A/Γ），
  则 G2 缝在"收缩原语"这一层就断了，只能退到 G1（整段替换）。
  **M135 注**：M121 已在本机 CANN 9.1.0 + `__mix__(1,2)` 的本形态下实测该通路可用（见 §7 表后的
  「M135 更正」块）⇒ 本失条件在**该形态**下未被触发；但 M121 对"别的 mix 配比 / 别的工具链版本"
  **未覆盖**，故它在这些未覆盖形态下**仍保留**；
- 若 `docs/15` §6.3 的整层下限 1.37 ms 本身被推翻（例如 368 T 是 36 子系统口径、实际 28 AIC 只有
  286 T ⇒ 整层 1.76 ms），倍数结论方向不变（8.8× 而不是 11.3×），
  **但"整层 1.37 ms"不能再被当成整层目标引用**。

## 6. 防 fork 堆积：针对"m18 是建好但从未集成的 fork"这条风险

### 6.1 风险为什么真实（不是猜的）

- `m18_gdn_prefill` 具备一个"完整交付物"的全部外形：独立 target、独立 host、4 档 PASS、审计脚本、
  证据归档 —— 但 `grep -rn "m18" m15_layer_loop/ | wc -l` → **0**（范围见 §1.2）。
- M101 的 `m15_attn_core` 也是同一形态（M103 §1.2 的 N2/N3 与 §2.0 的"仓库里已有两条更省事的先例"）。
- ⇒ **本仓库的默认激励是"建独立 target"**（开发快、验证干净、不碰共享热文件），而"集成"是最后一步、
  且天然会被推迟。M103 §2.0 因此**建议**各段先做独立 target —— 这条建议对**开发**有利，
  **但它正是 fork 的温床**。本文件认为需要给它加一条对冲。

### 6.2 建议的机制（五条，按"能不能被机械检查"排序）

1. **【最强】把"挂载点跑通一条最小档"写成段体 mission 的完成条件，而不是最后一步。**
   具体到 GDN：B1 的分支**必须**在 `m15_layer_loop.asc` 的档位表里出现一个 GDN-prefill 档
   （`ENTRY_GDN_PREFILL` 从那句 `// 预留，未实现` 变成真入口），并在该档上跑通
   —— 按人类裁决②，**档位应是真实 shape（prefill m=4097 / decode m=1 + ctx 4097）**，
   不是 m=64 之类的缩形档；缩形档可以当调试档，但**不能**当完成条件。
   **独立 target 可以存在，但它不能是唯一的运行路径**。这条可机械检查：
   "该 mission 的 diff 里是否同时含 `m15_gdn_prefill.*` 与融合 TU/资源头的挂载改动"。
2. **【强】段体不得定义第二套宿主接口。** 段体的 host 侧入口签名、GM 操作数布局、flagId/BufferID 段
   一律由 Wave A 的契约头提供；段体只允许 include "自己的资源头 + 契约头"。
   （M103 §2.5 已建议"段体只吃自己的资源头"，这里补上"加契约头、且不得自建第二套"。）
3. **【强】引入"影子对账"读数：段体交付时必须给一次"该段在融合 kernel 里确实被执行到"的证据**
   （例：在融合 kernel 的该档里打印/落盘该段的输入输出指纹，或该段的 probe 抽点），
   而不是只有独立 target 的读数。这把"集成"从最后的惊喜变成每段的可检查项。
   **注意口径**：这是**功能层面**的对账，**不是性能门限**（人类口径「现在先不关心性能」）；
   时间占比可以顺带记录，但不作为验收条件。
4. **【中】不允许"同类独立 fork 并存三个而融合 TU 里一个都没接"。**
   具体：**交付实现（mmad）的段体必须从第一天就挂在融合 TU 的挂载点上**；
   VF 对照实现如果单独建 target，**必须显式标注为对照路径**，且不得成为唯一的运行路径。
5. **【中】把 m18 的定位在文档里写死**（就在本文件这里）：
   **m18 = 判据/参考 + VF 子原语 donor**（`CumSumExpVF`/`GammaStrictVF`/`TrilSolveVF` 可原样复制），
   **不是"已完成的 GDN prefill 段"、也不是"待优化的生产段"**。否则下一个人
   （或在上下文压缩后的我自己）会把它当既成事实引用。

| 维度 | 打通阶段就要用的真实 shape | 现状（rev `20bd20d`） |
|---|---|---|
| GDN prefill | `m=4097` | m15 的 GDN 段是 decode 定尺（`M_MAX = 64`、`CHAIN_M = 1`）⇒ 必须改 |
| GDN decode | `m=1` + **context 4097** | 已有；`DECODE_CTX` 已于 M184 修为 4097（⇒ `DECODE_BLOCKS=257`、`DECODE_COMP_ROWS=1028`），与"context 4097"口径一致（M103 登记、M184 修） |
| MoE | `E=512`、`topk=10` | 现树是 **E=4 / topk=4**（golden 缩形档）⇒ 槽表与 router 都要换真 shape（M103 §1.3） |
| 权重 | 真实 checkpoint 切片 | 与 M93/M99 的 manifest 工作对齐（M103 §6.9） |

**注意这条与"性能不是本阶段的判据"不冲突**：真实 shape 是**功能正确性**的前置
（窄形档 PASS 不蕴含真 shape PASS —— 例如 MoE 的 `NUM_EXPERTS 4→512` 会改槽表与寻址，GDN 的
`m=4097` 会触发 m-tile / 尾块 / AIV 分派等一批在 m=1 下不可达的路径）。
⇒ **窄形档只能当调试档**，**不能**当 milestone 产物。

## 11. mmad 扫描的精度风险（**B1 的头号设计风险**）

> 塔的指派：这一节必须写出来。**本文件不猜 M106 的结论** —— 塔已派 **M106** 探针裁决
> 「cube 能不能吃 fp32 操作数」；下面按**两种分支**分别给出 B1 要怎么做。

### 11.1 三处数值最敏感的地方（都不是"越算越大"的那种，而是"链长 + 条件数"的那种）

| # | 位置 | 在 §4.4 的哪个缝里 | 敏感的原因 |
|---|---|---|---|
| 1 | **chunk 内 cumsum**（`ĝ = inclusive_cumsum(g)`，随后 `eg = exp(ĝ)`、`ig = exp(−ĝ)`） | `Scan_Scalar` | 链长 **BT=64** 的顺序累加；`exp` 把**绝对**误差放大成**乘性**误差；而 `ĝ` 的量级是 `g` 的累加（m18 归档 `max|exp|` 一项 = **1.854**，见 README §4.4） |
| 2 | **`(I+L)^{-1}` 三角求解**（`TrilSolveVF`，行串行 **BT 步**） | `Scan_SolveG` | 链长 64 的**串行递推**（不是归约、不可树化）+ 三角解的**条件数** `κ∞ = 3.2116`（m18 的 `m18_gdn_prefill/evidence/probe_geometry.txt` 归档值，由归档 A 复算） |
| 3 | **状态 S 的缩放与跨 chunk 递推**（`S *= egL`；`S += kᵀ·d′`，**65 个 chunk**） | `Scan_StateUpdate` + `Scan_Scalar` | 链长 **65×BT**；且 `egL < 1` 时前级误差被**衰减**、`egL ≈ 1` 时不衰减 ⇒ 误差可长时间不消（m18 实测 fp32 下每 chunk 边界 ~2e-7、"不随 chunk 数累积"，但那是 fp32 的结论） |

### 11.2 为什么"把 u 换成 bf16"会立刻出问题（用 m18 自己的 ε 结构与归档常数代入）

m18 README §4.2 的 ε 推导里，**链长项**只依赖 fp32 单位舍入 `u = 2^-24`：
`γ₁₂₈ = 128u/(1−128u)`（GEMM inner=128 顺序 FMA）、`γ₆₄ = 64u/(1−64u)`（行前代 64 步），
再乘三角解条件数 `κ∞ = 3.2116`（**归档值**，`m18_gdn_prefill/evidence/probe_geometry.txt`）。
**只把 `u` 换成 bf16 的 `2^-8`（尾数 7+1 位）、其余不动**：

```
$ python3 - <<'PY'
KAPPA = 3.211607375            # m18_gdn_prefill/evidence/probe_geometry.txt 的归档 kappa_inf
def eps(u):
    g128 = 128*u/(1-128*u); g64 = 64*u/(1-64*u)
    return KAPPA*(g128+g64) + 65*(2**-23) + 3.0e-7, g128, g64
for name,u in (("fp32 u=2^-24", 2.0**-24), ("bf16 u=2^-8", 2.0**-8)):
    e,g128,g64 = eps(u); print(f"{name:16s} gamma_128={g128:.3e} gamma_64={g64:.3e} -> eps={e:.3e}")
PY
fp32 u=2^-24     gamma_128=7.629e-06 gamma_64=3.815e-06 -> eps=4.480e-05
bf16 u=2^-8      gamma_128=1.000e+00 gamma_64=3.333e-01 -> eps=4.282e+00
```
`bf16` 那一行的 `γ₁₂₈ = 1.0` 就是经典的"累加误差 ≥100%"发散点（分母 `1−128u = 1−0.5`），
**`ε ≈ 4.28`（相对 `Σ|terms|`）已经完全失去判据意义**（m18 的 fp32 ε 是 4.48e-5 ⇒ 差 **9.6×10⁴ 倍**）。

**但这个代入只对"累加器本身是 bf16"成立。** 3510 的 cube 是 **bf16 操作数 + fp32 累加（L0C fp32）**
⇒ 真正会发生的是下面两种完全不同的情形：

| 情形 | bf16 从哪进来 | 后果 | 是否可用 |
|---|---|---|---|
| **A：只有操作数 bf16、累加仍 fp32** | 每次 mmad 前把操作数 round 到 bf16（相对 **2^-9 ≈ 2.0e-3**） | `γ₁₂₈` 仍是 fp32 的 7.63e-6；新增的是**输入量化**误差（约 2×2^-9 的产品级相对误差） | **需重推 ε 并重跑**（m18 README §8.4 已写明"换 bf16 需重推 ε 并重跑"）。**大概率可用**，但**必须实测** |
| **B：某条链连累加也只能 bf16** | 例如 cumsum 扫描、或三角求解的递推 | 上表的 `ε ≈ 4.28`，**界失去意义** | **不可用** ⇒ 这条链必须留在 fp32（VF） |

⇒ **这两条正好与 §10.2 的裁决映射互相印证**：cumsum（`Scan_Scalar`）与三角求解（`Scan_SolveG` 的前代部分）
**都不是"矩阵乘法"**，裁决不强制它们上 cube ⇒ **它们天然可以留在 fp32 VF**，
**而精度分析也正要求如此**。真正的风险集中在**那 6 个 mmad 收缩**（情形 A）。

### 11.3 两种分支下 B1 各要怎么做（**待 M106 裁决**）

**分支①：cube 能（有）fp32 操作数模式**（`docs/15:319` 的立场："fp32 的 cube 峰值 24 TFLOPS ≈ bf16 的 1/15"）

- B1 直接用 fp32 操作数做 mmad：**判据形态不变**（可继续用 m18 的 numpy fp64 紧容差逐句参考）；
- 代价（可算）：cube-fp32 下 chunk core 的 6 个收缩 = `36.0 GFLOP ÷ 24 TFLOPS = **1.50 ms/层**`
  （用 `docs/15` 的 31.2 GFLOP 口径是 1.30 ms/层）—— 比 bf16 的 0.098 ms 慢 15×，
  **但仍比 VF 的任何口径（0.81~3.25 ms）同量级或更快**，且**没有 hi/lo 的复杂度**；
- 需要重推的：fp32-cube 的累加仍应是 fp32（L0C），因此 `γ₁₂₈` 不变，**ε 结构基本可沿用**。

**分支②：cube 只能吃 bf16 操作数**（m18 README §7 的立场）

- **选项 2a：接受 bf16 判据** ⇒ 判据形态换成"bf16 三方 cross_check"（m18 README §7 的自述），
  ε 必须按情形 A 重推 + 重跑；**这是塔的裁决项**（M33 §9 存疑 3 的兄弟问题）。
- **选项 2b：hi/lo 双 bf16 拆分仿真 fp32**（塔提到的备选）—— 把操作数 `x` 拆成
  `hi = bf16(x)`、`lo = bf16(x − hi)`，用 **3 遍 mmad**（`hi·hi + hi·lo + lo·hi`）得到接近 fp32 的精度。
  **代价可算且不贵**：
  ```
  3 遍 bf16 mmad = 3 × 36.0 GFLOP ÷ 368 TFLOPS = 0.293 ms/层
  4 遍（若需 lo·lo）= 0.391 ms/层
  对照：单遍 bf16 = 0.098 ms/层；单遍 fp32-cube(24T) = 1.50 ms/层
  ```
  ⇒ **hi/lo 的代价（0.29~0.39 ms/层）比 fp32-cube（1.50 ms/层）还便宜约 4~5×**，
  且不需要新的硬件能力。**这是分支②下最值得先试的一条**（但拆分本身要额外 AIV 侧的 round/减操作，
  以及 L1/L0 的搬运翻倍，**未算过** ⇒ 进 §7）。

**B1 设计上应预留的东西（对两种分支都成立）**：

1. **dtype 策略不做成硬编码**：缝函数的签名（或编译期配置）要能表达"操作数 dtype + 是否 hi/lo"，
   否则 M106 一出结论就要动 6 个缝；
2. **累加一律 fp32**（L0C 本来就是）—— **不准出现"累加也只能 bf16"的链**（情形 B）；
3. **fp32 权威状态 vs cube 操作数副本的同步策略放在缝后面**（`GdnStateHome` 的一部分），
   不要把"每 chunk 把 S 量化成 bf16"写死在实现里；
4. **判据口径在 Wave A 就定死**（fp64 紧容差 / bf16 三方 / hi/lo 后仍用 fp64），
   **不要留到 B1 后期再选** —— 这是最容易返工的一处；
5. **精度预算表要在 B1 的设计里重推一次**：借用 m18 README §4.2 的**结构**
   （链长项 + `Exp` 的 1 ulp + 条件数放大 + 状态链），但 `u` 与各项系数按实际 dtype 换；
   m18 的 `κ∞ = 3.2116`（归档）与"误差不随 chunk 累积"（fp32 下的实测）**不能直接搬到 bf16 上**。

### 11.4 本节明确不做的

- **不猜 M106 的结论**（两种分支都写了做法，没有倾向性断言）；
- **不做原始误差分析**：11.2 的算法是"把 m18 自己的 ε 结构换一个 `u`"，这是**代数代入**，
  不是新的误差理论；情形 A 的"大概率可用"**必须由重推 ε + 重跑来关闭**，不是结论；
- **不声称"hi/lo 就能解决"**：它的代价算过（0.29~0.39 ms/层），但**拆分本身的 AIV 侧开销与
  L1/L0 搬运翻倍未算**（已进 §7）。
