# 统一数值验收口径（全仓库强制）

> 立此文件的直接原因：M24 与 M25 两轮 review 都抓到了「数字口径」类问题，而它们**不是** kernel 缺陷却被反复浪费轮次：
> - M24：README §5 引用了一个**不存在**的 `logs/check_ref_20260926.log`；把**首次不匹配值**（0.26/0.96/1.6e4）当作 max 来对比（真 max 是 4.17e4/7.66e2/1.68e4）；§5 说 `dbgc2` 恒 0 而实测 8184 非零。
> - M25：README 判据数自相矛盾——真值是 A 216 + B **614** + C 1 = 831，而 505 是 B 段的**打印行数**；831 里还混了 **108 条恒真 guard** 却未标注。
>
> 结论：口径不统一会让 review 判不了事，也让我们自己看不清进度。以下标准**所有 mission 一律执行**；与本文件冲突的旧写法以本文件为准。

## 1. 分层验收标准

### L0 — 单算子 / 单 kernel 级

| 项 | 要求 |
|---|---|
| 参考实现 | 必须有一份**独立**参考（numpy/double 或官方源码逐句复刻）。**「独立」分两层判，两层都要满足**：① **规则**来源独立（§1.2）；② **输入**来源合规（§1.3）。旧文那句「不许拿设备自己的中间输出当参考」**已废止** —— 它把「声明输入 / 上游输出 / 被判量自身产物」混成一条（§1.3 给了废止理由） |
| 容差 | **按数据域分档**（见 §1.1）：① **整数域/位域逐位**；② 浮点且参考能完整建模每一步舍入 → **≤1 ulp**；③ 浮点长累加链 / 在线重标定 / 含超越函数近似 → **推导出的界 + 逐元素检查**（`≤1ulp 比例`、`maxRel` 降为**报告项**）。**用哪一档必须在 README 写明理由** |
| 非空洞性 | 见 §4，缺一不可 |
| 设备侧自检 | kernel 内建判据（打印 checks/fails 计数）**必须**能与你归档的日志对上 |

#### 1.1 容差分档（2026-09-26 修订：不再对长 fp32 链一律要求 ≤1 ulp）

**为什么改**：`≤1 ulp` 在长 fp32 累加链上本质是**舍入一致性**判据——它测的是"设备与参考是否恰好把最后一位舍到同一侧"，这**不是正确性的性质**。两条实测证据：
- M24（attention decode）：4096 档退化为 `6143/6144 ≤1ulp`，唯一越界元素落在"相消区 + 贴 bf16 网格点"处（|out| 仅为同行量级的 1/200，参考值距网格点 1.17e-3 相对）。追这条"失败"花了好几轮，最终定位为**参考建模问题**（参考用全局 max 一次量化，而设备是逐 tile 用运行 max）+ **边界翻转**，不是 kernel 错。
- M27（L0 几何标定）：同一份数据里"首次不匹配值"被误当 max 对比过，说明**误差数字的口径**比 ulp 数本身更容易出错。
- 另一面：**真正抓到 bug 的判据**几乎都是整数域逐位与结构性判据（M32 的 ±Inf 靠逐字节比对；M24 的 P staging 索引错靠"只剩 4 个 row-group 活着"；M25 的 in_proj 缺独立来源靠 sha256 逐字节）。所以本修订**不降低**对真错的检出力。

**分档（用哪一档必须在 README 写明理由）**：

| 档 | 适用 | 判据 |
|---|---|---|
| **T1 整数域/位域** | 量化字节、scale、索引/topk、掩码、任何打包/位运算结果 | **逐位/逐字节，无例外**；**量化/编码类另须 §1.4 的定点方向判据**（只比 scale 字节不算通过） |
| **T2 可完整建模舍入的浮点** | 单次归约、顺序确定、无超越函数近似 | **≤1 ulp**；若参考值距网格点 `< δ` 则按 T2′ 判 |
| **T2′（T2 的边界子条款）** | 参考值距最近网格点 `< δ` | `≤2 ulp`（允许翻一次）**且**必须同时满足 `|out − ref| ≤ ε_acc·(Σ\|terms\|/den) + 0.5·ulp(out)`；**δ 必须推导**（形如 `δ ≈ ε_acc·Σ\|terms\| / ulp(out)`），并写明取值后果 |
| **T3 长 fp32 链 / 在线重标定 / 含超越函数近似** | **触发条件（满足任一即走 T3，无需再论证）**：① 含 `Exp`/`Log`/`Rsqrt`/`Rec` 等**超越函数近似**；② 含**跨 tile / 跨 split 累加或在线重标定**；③ 含 **mmad / cube 累加**（含 k>16 的内部归约）。例：online softmax、多 tile softmax、attention 的 PV/QK 累加 | `|out − ref| ≤ ε·Σ\|terms\| + 0.5·ulp(out)`（**参考为实值时**；**参考本身已被量化到 bf16/fp16 格点**时该项取 **`1.0·ulp(out)`**，理由见下方「`0.5·ulp` 还是 `1.0·ulp`」段），**逐元素检查**；**超界元素必须逐个有解释**，否则判 FAIL。`≤1ulp 比例` / `maxRel` / 位级一致率全部降为**报告项** |
| **T4 结构性（所有档都必须有）** | 全部 | 非空洞性（改输入必须改输出）、状态演化、索引/槽位可区分、dump 非零且位置正确、确定性（多次运行逐位一致） |

**两条护栏（防止用 T3 逃避 T1/T2）**：
1. **T1 数据不许降档**；档位必须在 README 写明理由，reviewer 有权把它打回更严的档。
2. **T3 的界必须推导**：逐项列出ε 的来源（mmad 的 `k·2^-24`、VF/combine 的若干 ulp、`Exp` 的**官方精度规格**等），并**逐元素**检查。**"实测最大 X ulp"不是界**——那是观测，不是推导。

**为什么 T3 必须有 `+0.5·ulp(out)` 这一半**：bf16/fp16 的**输出网格项**不是相对累加量级 `Σ|terms|` 的，因此在相消元素上任何"单一相对累加界"**必然不覆盖**（M24 实测：仅累加项越界 5820/6144；加 `0.5·ulp(out)` 后仍 1504/6144 ⇒ 那 1504 个正是 ≤1ulp 判据在边界元素上的固有现象，应由 T2′ 吸收）。

**`0.5·ulp` 还是 `1.0·ulp`：把"参考自身的量化"算进去（2026-09-26 tower 裁定，M36 实证）**

`+0.5·ulp(out)` 这一项**隐含"参考是实值"**。**当参考本身已被量化到 bf16/fp16 格点**（即参考也做了 `RndBf16` 一类取整）时，
**格点对格点的最大合法差就是 `1.0·ulp`** ⇒ 此时该项应取 `1.0·ulp(out)`。

- **为什么这不是放宽**：它**不放松**"参考为实值"那一支（那支仍是 `0.5·ulp`），只是**把参考自身的量化算进去**。
  否则每一个"贴着中点的元素"都会在下一个 mission 里重开一轮（M36 已为此烧过一轮评审）。
- **实例（M36，real_m1 `k=7253`）**：参考量化值 `0x3dc1` vs 设备 `0x3dc0` —— **相邻 bf16 格点、恰差 1 ulp**；
  真值 fp32 `0x3dc08001` = 中点 `0x3dc08000` + 1 fp32 ulp ⇒ **设备 ties-to-even 向下、参考向上，两边都合法**。
- **`BfUlp(v)` 的真值 = `2^(e-7)`**，其中 **`e` = binade 指数**（本文件的约定：`2^e ≤ |v| < 2^(e+1)`）。
  **为什么是 7 而不是 8**：bf16 = 1 符号 + **8 位指数** + **7 位显式尾数**；它的**有效精度是 8 位**
  （7 位存储 + 1 个**隐含前导 1**），但**相邻格点的间距只由 7 个存储位决定** ⇒ `2^(e-7)` = 1 个**格点间距**。
  **这条口径连续错了两代，原因都是「把隐含位当成存储位」**：
  旧式 `2^(e-1-8)` 把 binade 起点记错一位（只给真值的一半）；
  **M36 那轮的 `2^(e-8)` 又把 7 个存储位按 8 位算（仍只有一半）—— 本轮（M63）更正，这是修正一处 tower 口径错误**。
  自洽性检查：本段自己的 M36 实例说 `0x3dc0 ↔ 0x3dc1` 是「相邻 bf16 格点、恰差 1 ulp」，
  该值 binade 指数 `e = -4` ⇒ `2^(e-7) = 2^-11` ✓ 正是那两个位型在 f32 里的差（`2^(e-8)` 只给一半）。
- **同一个量、两套 `e` 的约定（引用时必须写明用哪套）**：若 `e` 取 `frexp` 的指数（`v = m·2^e`, `m ∈ [0.5,1)`
  ⇒ `v ∈ [2^(e-1), 2^e)`），则**同一个格点间距**写成 `2^(e-8)`。两式**不矛盾**，是 `e` 的定义不同 ——
  本仓 `m20_hyperconn/m20_hyperconn.asc` 的注释用的就是 frexp 约定（`2^(e-1-7) = 2^(e-8)`）。
  ⇒ 引用 ulp 口径时不能只说「用的哪个公式」，要写明**「哪个量（格点间距 / 最大舍入误差=半个格点）+ `e` 是哪套约定」**。
  实例复核（任一相邻 bf16 对都成立；`e` 取 binade 指数）：
  `0x3dc0→0x3dc1` 差 `2^-11 = 2^(e-7)`（`2^(e-8)` 给 `2^-12`）；`0x3ee7→0x3ee8` 差 `2^-9`；`0x3f80→0x3f81` 差 `2^-7`。

**报法**：`T? 档；ε 各项来源与数值；判定项越界数 / 总数；报告项（≤1ulp 比例、maxRel、位级一致率）`。**只给一个总数或只给 maxRel 不合格。**

#### 1.2 参考的规则从哪来（反自指 S2；M59 立，2026-09-26）

**先给代号（M59 的四种自指机理 + 不算自指的四类，后文只用代号）**：
**S1** 设备产物入参（参考的输入取自设备字节）／**S2** 无外部权威的规则镜像（参考的规则与设备出自同一份读法，无仓外工件钉住）／
**S3** 反演自消（参考用与设备同一约定的逆运算重建被判量）／**S4** 同一实现算两遍（同函数/同指针/机械 lift）。
不算自指的：**N1** 输入隔离（只用算件的声明输入做第一性原理复算）／**N2** 外部权威（规则钉在仓外工件上，代码里写出 `文件:符号`）／
**N3** 异实现或异数值域交叉（C++ 循环 vs numpy/BLAS、torch vs numpy、`expf` vs Reg `Exp`）／**N4** 结构性（§4 的 T4，**无正确性咬合力**）。
**本节治 S2**，§1.3 治 S1/S3，§1.4 是量化类的定点执行形态。

**规则**：参考实现所依据的**规则**（量化方向、舍入口径、掩码/位域约定、归一化顺序、平局规则…）必须钉在一个**不是本设备实现**的工件上，并在代码里写出它的 **`文件:符号`**。可接受的钉法（择一，README 须写明是哪一条）：

| 钉法 | 本仓实例（**按量写清，不要笼统说「某模块已有第二见证」**） |
|---|---|

| **仓外不可变对象**（checkpoint / 官方层模块字节） | 权重 `sha256`；L2 的 vLLM `qwen4_exp`（§1 的 L2 行） |

**m17 这条缺口的时间线与状态（按 §9.6 写清；也是「同源转录」的现成实例）**：M59 的风险表把
「m17 的 `quant_hw` 未引任何外部 `文件:符号`」列为 **R2**（它托着 m17 的 S5/S7 与 e2e 字节判据）；
**M60**（`feat/m60-m17-quant-rule-external-pin-and-witn`，commit `13d601f`；**as-of `29ca034` 记为未合入，现已随 `57f896c` 合入 main**，分支 tip `f4a2f42`）

**同源转录（correlated transcription）**：同一作者对**同一份规范**的第二次转写**不计为独立来源**。
它是合法实现、也可以是有效的第二见证（能抓笔误、尾部处理、VF vs 标量的分歧），
但**必须在 README 显式声明它是同源转录**，**不得**写成「两处独立实现」。
（实例：`m2_mxfp4_quant` 与 `m5_swiglu_quant` 各自的 `ocp_numpy`。）

**怎么判（可执行）**：
1. `grep -nE '[A-Za-z0-9_./-]+\.(h|hpp|py|md|json)(:[0-9]+)?' <模块>/README.md` 看验收节里有没有**仓外或跨模块**的 `文件:符号`（只引本模块自己的文件名 = 不合格）。
2. 逐个核对该 `文件:符号` 的**符号**在**被引工件**里存在：`grep -n '<符号>' <被引工件>`。**只有行号、没有符号 = 不合格**（§8.2）。
3. **反例（怎么算违反）**：规则与设备实现出自**同一份读法**，且没有任何仓外/跨模块工件钉住其语义。
   `m3_grouped_gemm` 就是这一形态：host `QuantRowH` 与设备 `M3VfQuantTwoGroups` 同为 `2^(byte-127)`，
   两侧一起错 ⇒ pack 字节 **94.8% 不符仍全 PASS**（M59 标尺；归档 `m3_grouped_gemm/evidence/m54_quant_rebaseline.log`）。
   **该缺陷已由 M54 修**（e8m0 收敛到 floor/OCP、data 缩放方向改为 `halfScale`，**已并入 main `29ca034`**；
   新增的独立见证是 `m3_grouped_gemm/check_m13_cross.py`，含 legacy ceil 负向对照）。

#### 1.4 T1 的定点方向判据（量化/编码类强制；M59 立，2026-09-26）

**为什么**：只比 **scale 字节**的 `vf-probe` 型判据看不见 **data 侧的方向翻转** ——
`floor`（OCP）与 legacy `ceil` 两个规则在 `amax ∈ [4,6]·2^k` 内**同解** ⇒ scale 字节相同而 data 可能整体错。
m3（**M54 之前的 main**）的 `h_quant` 正是这样：**94.8% 的 pack 字节不符而全 PASS**（M54 已修，见 §1.2 第 3 条）。
定点方向判据用**一条固定输入**把方向钉死：方向对错给出不同的 `(scale 字节, data code)`。

**规则**：凡带**倒数/方向关系**的量化、反量化、编码算子（E8M0 × E2M1、MXFP4 pack/unpack、任何 `scale`/`halfScale` 互逆对），
验收必须有**一个固定输入用例**：构造 group 使 `amax` 取**定点值**，并**同时**核对 `scale 字节` 与 `data code`。

**定点读数（前四列 = M59 实测；最后一列是推导，它的值取决于平局口径 —— 见下）**：

| 组内 `amax` | 正确实现（OCP/floor）scale 字节 | data code | 反量化 = `amax` | 方向反了（乘 `scale` 而非 `halfScale`）：`h·scale` → code |
|---|---|---|---|---|
| **1.0** | **125** | **6** | 1.0 | `1.0×0.25 = 0.25` ⇒ **平局**：`tie-away`（`e2m1_encode_away`，即 `quantize_ocp` 的 CAST_ROUND）**code 1**；`tie-even`（legacy `e2m1_encode`，pre-M54 m3 的写法）**code 0** |
| 0.5 | 124 | 6 | 0.5 | `0.5×0.125 = 0.0625` ⇒ code **0**（两种平局口径相同，离最近格点很远） |
| 2.0 | 126 | 6 | 2.0 | `2.0×0.5 = 1.0` ⇒ code **2**（恰是格点，无平局） |

⚠ **读数必须连口径一起引用**：`amax=1.0` 那一格是**精确平局**（0.25 夹在 E2M1 的 `0.0`(code 0) 与 `0.5`(code 1) 正中间），
所以它的反向 code **在两种平局口径下不同**（1 / 0）—— **只写一个数而不写口径就是不可复现的读数**。
M59 原文写的「方向反了给 code **0/1**」正是这个二义（未指明口径）；本表把它拆开写清。
**判据本身不依赖口径**：两种口径下反向 code 都 **≠ 6** ⇒ 负向对照照样 FAIL。

**怎么判（可执行）**：
- 参考侧（本仓可跑；`quantize_ocp` 是官方 ops-nn 的逐句转写，见 §1.2）—— 一行命令同时给出正确值与**两种平局口径**下的反向值：
  ```bash
  /usr/local/python3.12.13/bin/python3.12 - <<'PY'
  import sys, numpy as np; sys.path.insert(0, 'tools/golden'); import moe_block_ref as M
  for amax in (0.5, 1.0, 2.0):
      x = np.zeros((1, 32), dtype=np.float32); x[0, 0] = np.float32(amax)
      qx, sc = M.quantize_ocp(x); b = int(sc[0, 0]); h = np.float32(amax)
      rev = np.array([[h * np.float32(2.0 ** (b - 127))]], dtype=np.float32)   # 方向反了：乘 scale
      print(amax, b, int(qx[0, 0]) & 7, int(M.e2m1_encode_away(rev)[0, 0]) & 7, int(M.e2m1_encode(rev)[0, 0]) & 7)
  # → amax  scale字节  正确code  反向code(tie-away)  反向code(tie-even)
  #    0.5      124        6            0                  0
  #    1.0      125        6            1                  0
  #    2.0      126        6            2                  2
  PY
  ```
- 设备侧：同一固定 group 的 dump 里 `(scale 字节, data code)` 必须与上表**同 `amax` 行**逐字相同。**只报 scale 字节不算通过。**
- **负向对照**：把方向改反（乘 `scale = 2^(byte-127)` 而不是 `halfScale = 2^(127-byte)`），该用例必须 **FAIL**
  （code 变成 `1/0/2`（tie-away）或 `0/0/2`（tie-even）—— **一律 ≠ 6**）。
  旧式只比 scale 字节的判据在这种改动下**仍然 PASS** —— 这正是本条款要补的洞。
- **判据**：量化/编码类 README **没有**这条定点用例 ⇒ **P2**；有但只核 scale 字节、不核 code ⇒ **P1**（等于没补）；
  **反向读数不写平局口径** ⇒ **P2**（不可复现，与 §9.2 的「计数要交代口径」同族）。

## 2. 判据的写法规范

1. **判定项与报告项分栏**：PASS/FAIL 计数里**只能**含判定项。guard（恒真检查、非空洞性检查、状态演化检查）是报告项，必须单列并写明它检查什么。
2. **计数必须可复算**：README 里的 `A 216 + B 614 + C 1 = 831` 这种式子要能逐项对上代码；**不要**用「打印行数」当判据数。加了判据就同步改总数。
3. **数字口径三件套**：任何误差数字必须标注是 **max 还是首次不匹配**、**相对还是绝对**、**在哪一档输入上**。
4. **引用必须存在**：README/commit message 里引用的日志、dump、脚本路径必须**在该 commit 里真实存在**。
5. **证据可离线复现**：判据要能由 reviewer 用归档数据 + 一条命令重跑；dump 的 `sha256` 必须入库（例：`evidence/dump_sha256.txt`）。
6. **同一 commit 自洽**：README 里的数字与同 commit 的 evidence 目录必须一致；改代码就同步改 README，反之亦然。

## 4. 什么算「非空洞」

每份验收必须至少包含下列**相关**项（按被验对象选择，不可全缺）：

- **输入敏感性**：改动输入 → 输出必须变（防「恒输出常数也能过」）。
- **状态演化**：有状态的算件（GDN 的 conv/ssm state、KV cache）必须证明跨 token 确实在演化（例：`hout != hin`、逐层 evolving 计数）。
- **dump 非零且位置正确**：中间张量 dump 的非零区间必须落在预期位置（M24 的 `gp.bin` 就是靠这个抓出 unit 索引空间错位）。
- **槽位/层号可区分**：跨层/跨槽位的算件要有独立来源的判据（例：权重槽位 `sha256` 校验），不能只靠「同一个指针算两遍」。
- **确定性前提要实测**：若用「逐字节对比」当判据，必须先证明 kernel 本身是确定性的。
- **反自指检查（M59 立，2026-09-26）**：每条判定项必须能回答「**若本算件有一个规则/方向级错误，它会不会 FAIL**」。
  **答不出的不得计入 PASS 计数**，须单列为报告项，并写明为什么答不出。它是 §1.2（规则来源）/§1.3（输入来源）在计数口径上的执行面。
  - **怎么判（可执行）**：对每条判定项写一行「**它能 FAIL 掉的错误类别**」。对量化/编码/掩码/索引类，逐条回答 §1.2 的 S2 问句
    （规则钉在哪个 `文件:符号`）与 §1.3 的 S1/S3 问句（输入是①②③哪一类、有没有反演自消）。
    报告形态固定为：`判定项 N 条 = 有咬合力 M 条 + 反自指检查不过 K 条`，且 **K 条不得进 PASS 计数**（§2.1 的分栏要求）。
  - **负向对照（防「口号式声明」）**：把该算件的规则/方向**故意反过来**跑一次，凡被声明为「有咬合力」的判定项**必须至少有一条 FAIL**。
    可抄的本仓实例：m3（M54）的方向反转对照（pack 字节 94.8% 不符）、M59 在 m1 golden 上的 44.2% 复算、以及 §1.4 的定点方向判据。
  - **判据**：README 只写「参考是独立的」而**列不出**每条的「能 FAIL 的错误类别」⇒ **P2**；把答不出的项算进 PASS 计数 ⇒ **P1**（计数虚高，与 §2.1、§9.2 同族）。

## 5. 与 vllm-ascend 目标的关系

最终目标是让这张卡能推理 Qwen3.8-Flash-Next-MXFP4，**用户已裁：每个 kernel 只跑一层，48 层循环留在框架侧，对 vLLM 的修改要小**。因此：

- L2 级的参考实现**天然就是**官方 vLLM 的 `qwen4_exp`；我们不要在仓库里另造一套「整网 golden」当权威。
- 每个 per-layer 算子的接口应尽量对齐 `qwen4_exp` 层模块的既有张量契约（hidden in/out、KV cache、state），这样 L2 验收可以直接复用框架侧的对拍路径。

## 7. 附则：固有验收偏差与已接受偏差（2026-09-26 tower 裁决）

**事实**（M33 调研，`docs/15` §9 存疑 3）：官方 QSA 的 `indexer_budget=2048` 是 **token** 预算 ⇒ `block_topk = 2048/4 = 512` 块；而 4097 上下文的可见块是 ⌈4097/4⌉ = **1025** 个。**官方只 attend 2048/4096 个历史 token**（decode 档 context=4096 时同理）。⇒ **稠密 causal 与官方输出在任何长度下都不可能一致**（gather 集合与 softmax 分母都不同）。

**裁决三条**：

1. **首期验收基准 = 自建稠密 causal 参考**，但任何文档/README 提到 m=4097 或 decode-ctx4096 的数值验收时，**必须**写明「本基准是自建稠密 causal 参考，与官方 vLLM 的 QSA 输出存在固有差异（约一半历史被截断）」。**禁止**再出现「m=4097 对齐官方输出」这类自相矛盾的表述。
2. **QSA 的缓存填充必须在首期就做**（raw key ring + compressed key cache；压缩行在 position 3,7,…,4095 共 1024 行；**pos 4096 因 `(4096+1)%4==1` 属"开放组"，只作 causal 尾部 token、不写 compressed cache**）。缺了它，后续接真 QSA 要重做整条 KV 路径。
3. **打分 / topk / expand 是「支持 qwen4_exp」之前的必做项**——理由是**正确性**（不做则输出 token 与官方不同），**不是**性能（省下的算力只占全 pass 下限约 1.1%，Ascend 上 topk 是排序难题）。它只是排在后面，不是被砍。

**因此**：M39 产出的 CPU 参考若直接跑官方层代码，attention 段的 dump 是**官方稀疏输出**，必须如此标注，**不得**被别的 mission 当作稠密判据使用。

### 9.1 规则① host 墙钟计时在共享卡上不构成证据

**规则**

1. host 侧「**N 次连发 + 一次 sync 的墙钟**」在共享 NPU 上**不构成证据**。**即使补了抖动范围，它也仍然只作定性** ——
   **作数的性能数字一律走设备侧 `msprof`**（第 2 条），host 读数在任何形态下都**不进判定项**。
   报出分布是**描述性义务**（让人看出它有多不可靠），**不是**把它升级成证据的路径。
2. 要作数的性能数字用**设备侧口径**（`msprof` 的 kernel 时间），或明确写在**静场/独占窗口**下采集，
   并给出「怎么确认是静场」的依据。
3. **抖动幅度大于待断言的差异时，不得下结论。**
4. **已归档的 host 墙钟数字不必回头重测**，但凡将来**引用**它们，须要么补上抖动范围，
   要么标注「该方法在共享卡上不可靠，仅定性」。

**为什么「带范围」也不够（M63 补，承 M55 r4 评审的强化建议）**：**抖动很小的 host 读数最会骗人** ——
`m15_layer_loop/evidence/p1_timing_distribution.log` 的表头引用了「review r2 实测 24×」这条一般性事实，
而**该文件自己的 P1 五次读数只抖 1.09×**（24.970 / 27.293 / 25.032 / 24.972 / 25.342 ms）；
**同一次采集**里 P3 却抖到 **6.5×**（8.505 → 54.997 ms）。⇒ 同一份归档里的 host 读数，可信度**逐行不同且不可预判**：
「补了范围」只说明**这一次**抖了多少，**不把这一行数字变成证据**。要作数仍走 `msprof`（同批设备侧读数与归档表**五对逐对差 ≤1.3%**，见下）。

### 9.2 规则② 统计/校验工具必须交代自己真正的覆盖范围

**规则**（凡「统计 / 校验 / 对账 / 复现」类工具）

1. **覆盖率计数只能由与匹配器同一份正则 / 同一份遍历产出**（不要一份正则去匹配、另一份手写数字去报）；
   计数与 list 必须**同一次运行**产出。
2. **汇总必须三态分栏**：`verified / unverified / out-of-range`（或等价三栏）。
   **「跳过 / 无法判定」必须是可见的一栏，不是沉默。**
3. **必须做一条「已知会被漏掉」的负向对照**：找一条**匹配器本来就看不见**的样本
   （另一种写法、另一个同名文件、简写形态），确认它**被报成 unverified 而不是被当成通过**。
   **「0 问题」若没有这条对照，只等于「我的匹配器看不见问题」。**

**触发事件（一小时内三次，都是工具、不是被测对象）**

### 9.3 规则③ 脚本运行时打印的断言性文字也是证据

**规则**

1. 凡脚本/内核在**运行时打印、写盘或落进 dump/日志**的断言性文字（「正在修 X」「暂不支持 Y」「TODO：Z」），
   **都属于证据的一部分**，必须与**同 commit 的事实**一致 —— 与 README/文档的要求同级。
2. 过期结论一律改成**可核对的现状陈述 + 出处**（例：把「device kernels miss the `:413` override
   （M32 is fixing it）」改成「截至 X，device 侧已具备该 override，见 m2/m5/m13」并给出可复算判据，
   如 `grep -c 0x7F81` = 3）。**不要只把旧句删掉** —— 删掉会让「曾经缺过」这段历史消失，
   **改写成现状 + 出处**才既正确又可追溯。
3. **评审判据**：日志/打印里出现过期断言 ⇒ **P2**（不阻塞结论，但要改）；
   **若它已持续混进多份归档日志 ⇒ 升 P1**（因为它污染的是**证据本身**）。

**触发事件**：M51 一轮报出 **4 处**过期的 "M32 is fixing it"，其中一处是 **`tools/golden/selfcheck.py`——
它在运行时被打印出来**。这比「文档里写过时话」严重一档，因为：**每跑一次，这句过期断言就被写进一份新的日志** ⇒
**过期的文字会持续污染新产生的证据**，后来的读者看到的是「最新日志里的那时的话」，很容易当成当前事实。
而 M32 那条早已在 main 上修好（`MxQuantComputeScale` 在 m2/m5/m13 三处均含该 override，`grep -c 0x7F81` = 3）。

**同族**：§2.4（引用必须存在）、§8.2（以符号定位）、§9.1（测量手段先成立）、§9.2（计数同源）、§8.3（不无输入发合格证）。

### 9.4 规则④ 判据/参数对账：评审固定做逐参数对账

**规则**：判据/参数有两类「改松」——

- ① 直接**把界改松**（评审本来就会看）；
- ② **换了参数（或其表达式/实参）却声称「同口径」** —— 这一类**从通过/失败看不出来**
  （当轮可能离生效点极远、照样 PASS，甚至原判据本来就过）。

因此**评审固定动作**：对「影响判定阈值的参数/表达式」**逐一比对 `main` → `tip`**（不只是核作者自己声明的那一处），
并核对 README/commit 里「同口径」这句措辞是否成立。

**触发事件**：**M47 r1（判 P1）**——验收 harness 里 `ValidateSlot` 的 `rowMaxGu` 形参被传成了 **`rowMaxDn[s]`**
（main 是 `rowMaxGu[s]`），使 16 条 gate_up 判定项的容差按 **down（K=640）** 权重的列最大值缩放
（用真实权重复算，逐列比值 ∈ **[0.094, 8.0]**，部分列阈值放宽 **8×**、其余收紧最多 10.7×）；
而 README/commit 都以「**改前同口径 32 条**」呈现。当轮 `maxRelDiff` 全 0、离生效点极远，
且用**未修改的 main 构建**证明原判据本来就过 ⇒ **不是「为了让跑过而改」，就是一处未声明的换参**。
**M47 r2** 据此做了**完整的逐参数对账**（`CheckBlock` 全函数体 md5、gate_up/down 的四个实参
含 `50.59644260968681`/`25.298221281347036` 与 rowMaxA/Gu/H/Dn 的配对、bf16 网格化与 relDiff 分母口径、
输入生成、参考链、host 量化镜像），结论：「**除已声明的一处（h_quant info→T1 判定项，属收紧）外，
没有第二处「换了参却声称同口径」**」。

**评审判据**：README/commit 声称「同口径」而**未给逐参数对照** ⇒ **P2**；
发现**未声明的换参**（尤其放宽）⇒ **P1**（照 M47 r1 处置）。

### 9.5 规则⑤ 核对本 mission 变更集一律用三点 diff

**规则**：核对「本 mission 改了什么」，一律用 **`git diff --name-status main...HEAD`（三点）**，
并在报告里**写明你用的是三点**。若确要给两点 diff，**同时给出 `git merge-base main HEAD`**，或干脆只给三点。
引用「范围/变更集」时不要只写命令 —— 要写清它是**三点还是两点**，否则读者复现出来的会是另一份清单。

**原因**：rebase 之后，`oldtip..newtip`（两点）会把你 rebase 期间**吸收进来的 main 自己的进展**算作「你的变更」；
三点从 merge-base 起算，只反映分支真正的增量。

**触发事件**：**M51 交卷时**主动说明两点 `main..HEAD` 会显示大量「反向」变更（因 main 已前进，
且被后合入的 M48/M24/M49 与 `m10_attn_decode` 删除干扰）；随后 tower 发现**自己给 M40 reviewer 的检查指令写错了** ——
让它看 `git diff --stat ab746c5..bf592f9`，而该分支已 rebase 到更新的 main（merge-base 从 `55f5e18` 前进到 `4ba5484`），
这个**两点** diff 显示 **532 个文件、全是 main 新增的**。

当时改用的**三点** `git diff --name-status main...bf592f9` 得到 **22 个路径，全在 `m15_layer_loop/**`** —— 这才是真的。
⚠ **这条三点读数带一个时间窗**：`bf592f9` 后来**已并入 main**，故**在今天的 main 上复现三点 diff 是空的**（自己减自己）；
两点读数 `git diff --stat ab746c5..bf592f9` = **532 文件**则**永远可精确复现**（它不依赖 main 的位置）。
⇒ 引用"当时"的范围数字，要么写清**当时的 main 是哪一支**，要么改用两点 + `merge-base`（本规则第 2 条）。

**评审判据**：报「范围/变更集」而**未声明三点/两点**、或据两点 diff 下结论 ⇒ **P2**（结论可能不成立）。

### 9.6 规则⑥ 引用尚未合入的内容必须标注分支与状态（M63 立，2026-09-26）

**规则**：一份**引用**由三件东西构成，缺一不可：**① 路径/符号**（§8.2：以符号为准） + **② 该代码/文件所在的分支** + **③ 引用当时它是否已合入**。
**未合入时的正确写法**（照抄这个形态）：`<路径:符号>（分支 <branch>，截至 main <short-sha> 未合入）`，
或 `…（已随 <commit> 合入 main）`。**未合入**的引用**必须**带这两个标注，否则读者会把它当成 main 的现状。

**触发事件（这次是 tower 自己犯的）**：tower 给 M55 派单，要求 reviewer 按 **`docs/17 §9.1`** 核对某条规则 ——
而该章节当时**只存在于未合入的 `feat/m55-*` 分支**上（main 的最后一节是 §8.4）。
reviewer 在 main 上找不到 `§9.1`，只好先自己判定「这是派单写错还是自己找错」，白花一段排查时间。
同族事件：M59 通读 m21 的参考时读的是**当时未合并**的 `wt-39`（`feat/official-qwen4exp-single-layer-cpu-refer`，其后随 `7c6ee12` 合入 main），
报告里被迫自陈「读到的是分支状态」。

**怎么判（可执行）**：
- 机械筛：`git show main:<被引路径> 2>&1 | head -1` —— 若报 `fatal:` / `does not exist` ⇒ 该引用**不在 main 上**，必须补②③两个标注。
  章节引用用 `git show main:docs/17-verification-standard.md | grep -c '^### 9\.1'`（命中 0 ⇒ 未合入）。
- 扫描纪律（与 §9.2 同族）：**凡引用本仓路径/符号的文档或派单，逐个跑上面这条命令**；只在 main 上存在的引用可以不写②③，其余一律写。
- **评审判据**：引用未合入内容而**未标注分支与状态** ⇒ **P2**（读者无法判断引用的是哪一版事实）；
  据此下结论（「main 上已经这样做了」）⇒ **P1**（结论可能不成立，与 §9.5 的「两点/三点」同族）。

### 9.7 规则⑦ 读数须与自己的命令输出同源；跨 rev 不得拼分子与分母（M125 立，2026-10-04）

**规则**

1. 写进 README / 文档 / 报告的**读数**，必须来自**本人在该 tip 上实跑**的命令输出，或本仓归档里**可指名到 `文件:行`** 的既有读数。**引用他人（或他档归档）的读数时必须写明出处**（§9.6 的三件套照旧），**不得**把它当作自己当场跑出来的证据。
2. **跨 rev（或跨次运行）比较同一条判据时，不得把不同 rev / 不同次运行的分子与分母拼在一起**：要么在**同一 rev** 上把两段都重算，要么在文里**逐段写清各自来自哪个 rev / commit**（§11.5 的「命令 + commit + 当场读数」）。
3. 本条与 §9.2 第 1 条（工具的覆盖率计数与匹配器同源）、§10「分子与分母同源」同族：那两条治的是**一次运行内**的分母 / 分子同源，本条补的是**跨运行 / 跨 rev / 跨作者**的拼接口径。与 §1.2 的「同源转录」区分开：§1.2 说的是**参考实现的规则**来自同一份规范，本条说的是**读数**来自自己的命令。

### 9.8 规则⑧ 有界等待未取得读数须记为「未取得读数」，不得记为「未复现」（M125 立，2026-10-04）

### 9.14 规则⑭ 钉 rev 的审计文档：行号是审计记录，引用侧保持声明 rev、不得刷到当前 main（M137 立，2026-10-04）

5. 本条与 §8.2 相邻：§8.2 已把归档证据（日志 / dump 清单 / sha256 文件）里的行号列为**例外**（采集时刻的事实），钉 rev 的审计文档属同一类「行号 = 采集时刻事实」；本条补的是**引用侧不得刷新**这一半与**混基准**的识别。与 §9.6 同族：都治引用的基准 —— §9.6 治分支 / 合入状态，本条治 rev 行号基准。

### 9.15 规则⑮ 禁用词（六词）规范：绝对化措辞不得进陈述文本；清单须在仓内可独立核对（M175 立，2026-10-04）

**规则**

1. **禁用词表（逐字，六条）**：`已全部`、`无残留`、`0 命中`、`零命中`、`绝不`、`完全正确`。
   这六条都是**绝对化 / 无条件**的措辞：`已全部` 与 `无残留` 声称穷尽且无遗留；`0 命中` 与 `零命中`
   把「某个 pattern 在某个范围内没命中」写成不带范围的结论；`绝不` 是无条件禁止 / 保证；`完全正确`
   声称无保留的正确性。一律**不得**出现在任何 mission 的**陈述文本**里（README / CONTRACT / docs /
   脚本注释 / 提交信息）。
2. **替代写法**：把范围写出来 —— 「在 pattern `X`、范围 `Y` 上**未命中**」（同族 §9.2 与塔 2026-09-27
   广播的口径：一条 `grep` 的「没命中」只能支撑「在该 pattern 与该范围上没命中」，不能升格为「不存在」）。
3. **扫描范围**：某 mission 的**新增 / 改动陈述行**（用该 mission 的 base 做 `git diff -U0 <base>..HEAD`，
   只看 `^+` 行）。**不在范围内**：① 引用的他方原文（引文要逐字，见 §9.9 与
   `docs/evidence/quote_refs/README.md`）；② 归档证据 / 日志（采集时刻的事实）；③ **本节 §9.15 自身** ——
   它是六词清单的**定义处**，按构造必然含这六条字面。
4. **可粘贴的复现命令**（按要核的对象选一条）：

   ```bash
   # (a) 扫某 mission 的 diff 新增行（把 <base> 换成该 mission 的 base rev）
   git diff -U0 <base>..HEAD | grep '^+' | grep -nE '已全部|无残留|0 命中|零命中|绝不|完全正确'

   # (c) 目录级、排除本登记文件（§9.15 是六词的唯一合法载体）
   grep -rnE '已全部|无残留|0 命中|零命中|绝不|完全正确' <dir> | grep -v 'docs/17-verification-standard.md'
   ```

   **自命中说明**：本节按构造含这六条 ⇒ 命令 (a) 扫到 `docs/17` 的 §9.15 改动行时会命中该定义块；
   复核时把该块剔除（或用 (c) 排除本文件）。**命中只在 §9.15 定义块之外才算**。
5. **评审判据**：陈述文本出现六条之一而**未给范围** ⇒ **P2**；据某条把「某 pattern 在某范围上没命中」

   覆盖范围」）。
